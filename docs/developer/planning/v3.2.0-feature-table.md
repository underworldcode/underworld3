# Underworld3 v3.2.0 — features, readiness and test evidence

Draft for @lmoresi and the Steering Committee. **This is not the release manifest.** It is a
proposal for what v3.2.0 should announce and at what level, with the evidence behind each claim.

Built from all 186 PRs merged into `development` since v3.1.0 (8 July 2026), clustered by PR body
and changed files; every cited test and docs page was then opened to check the attribution.

## What TRL means

Technology Readiness Level is a 1–9 scale, originally NASA's and adopted by the EU for Horizon
Europe funding. It measures how ready a capability is, not how good the code is and not how much
of it there is. The levels below are UW3's reading of the EU definitions. Every organisation that
adopts TRL for software writes its own, because the EU text is one line per level.

| TRL | EU wording | For an Underworld3 feature |
|---|---|---|
| **1** | Basic principles observed | The method exists in a paper or a derivation; no code |
| **2** | Technology concept formulated | A prototype in a notebook or a branch; nothing integrated |
| **3** | Experimental proof of concept | On `main` and runs, but tests are absent, `tier_c`, or failing |
| **4** | Technology validated in a lab | Integrated, with `tier_a`/`tier_b` tests that pass on the release candidate |
| **5** | Validated in a relevant environment | Runs on the production stack (Gadi, container, MPI) on a realistic problem |
| **6** | Demonstrated in a relevant environment | A user-facing documentation page **and** a runnable demonstration; the owner commits to support it |
| **7** | Prototype in an operational environment | A group outside the developers uses it for real work |
| **8** | System complete and qualified | The Steering Committee signs it off at this release |
| **9** | Proven in an operational environment | Held at 8 across four consecutive quarterly releases |

**Tests can only ever evidence TRL 4.** Levels 5–9 rest on production use, documentation,
external adoption and committee sign-off, none of which a test suite can witness. The bar for
*Supported* here is **6**: the first level at which a user can find out how to use the feature and
someone has undertaken to support it.

Announcement bands: **Supported** = TRL 6+ · **Preview** = TRL 4–5 · **In development** = TRL ≤ 3.

The levels are cumulative, and a feature announces at its *weakest* part. Three entries below
(`fault-networks`, `transport-histories`, `constitutive-models`) bundle a sub-capability at 6 with
others at 3–4, so all three come out Preview. Splitting those keys would let the mature half be
announced properly.

## Reading the test columns

Test *files*, in the three categories that exist in this repo:

- **ordinary**: `tests/*.py`. Run in CI, but **serially**; the standard levels invoke plain `pytest`, never `mpirun`.
- **MPI**: `tests/parallel/test_*.py`. Run under `mpirun` by `test_levels.sh --parallel`.
- **ptest**: `tests/parallel/ptest_*.py`. Shown as *collectable / total*. These match no collection
  pattern (`python_files = test_*.py`) and so have **never been executed** by any run, in CI or locally.

The *4-rank* column reports what happened on 2026-09-24, when every category was run at
`mpirun -n 4` for the first time.

## Where "Improved" features sit on the TRL scale

TRL describes the current state of a capability, not how much changed. An entry is rated on the
evidence that exists today rather than on the size of this quarter's work. That has three
consequences here.

- **A long-standing feature that was already documented and demonstrated stays at 6** however much
  work went into it. `checkpoint-restart` and `data-access-array-contract` are both *Improved* and
  both sit at TRL 6. The improvement did not raise them, because they were already there.
- **An improved feature with no user-facing page stays at 4** however substantial the improvement.
  `interpolation-and-evaluation` absorbed the point-locator rework, the RBF fallback ladder and cheap
  foreign-point rejection, and its documentation moved by **two lines**. Preview is the right call.
- **Work can therefore be large and invisible to TRL.** `parallel-robustness` (15 PRs) and
  `jit-compilation` are *Fixed*: corrections to long-standing code that restore intended behaviour
  rather than extend it. They stay at 4 because nothing about their documentation or demonstration
  changed.

Kind and TRL answer different questions. Kind says what happened this quarter, which is what the
release notes report. TRL says how ready the capability is now, which is what the announcement bands
derive from. A feature can be New at TRL 4 (`solver-control-and-reporting`) or Improved at TRL 6
(`materials-system`) with no contradiction.

The **Docs Δ** column shows the pattern: features whose documentation moved a lot this quarter are
generally the ones that reached 6, and the two with no prose page at all (`free-surface`,
`boundary-flux-recovery`) are capped at Preview however much code landed.

## What the 4-rank runs found

| Category | Result | Nature |
|---|---|---|
| ordinary tests of the three features with no MPI coverage (18 files) | **587 / 590 pass** | 3 failures, all in one file |
| the MPI suite (42 files) | **157 pass, 1 fail** | the failure is *not* a parallel defect |

**`tests/test_0071_index_swarm_proxy_location.py`: 3 test bugs.** Each asserts an *existential*
claim against rank-local data (line 80: `results["nodes"] > 1e-2`, "some node is visibly wrong").
That holds globally but fails on a rank whose subdomain misses the material interface. Line 79 of
the same test asserts `max < 1e-5`, a *universal* claim, and is decomposition-safe. One MPI
reduction per assert fixes it. The product code is fine.

**`tests/parallel/test_1063_constrained_freeslip_parallel.py::…[ti]`: an accuracy regression.**
Partition independence *passed*; the `accuracy_anchor` failed. Mean-stripped topography moved from
the recorded **37.078 to 37.753 (+1.8 %, rtol 1 %)** on an identical mesh, reproduced exactly at
2 ranks. `iso` passes. Issues #495 and #564 covered this test's earlier partition-dependence and are
closed; the anchor was re-recorded in August, so this movement is new and unreported. Related open
issue #747 (the #457 transpose surviving in `SNES_Scalar`) is the right family.

**`tests/parallel/ptest_0844_reconnect_parallel.py::test_adapt_with_repair_runs_in_parallel`: a real
parallel bug.** Hangs in `uw.mpi.comm.allreduce` (line 174) because some ranks enter the collective
and others do not. Seven closed issues share this shape (#627, #346, #314, #512, #513, #351, #506),
none of them about `reconnect`. It surfaced only because these files ran for the first time.

## Three things to decide

1. **`fault-networks` is one rename away from being well covered.** 11 of its 12 `ptest_` files are
   genuine tests, and 99 of their assertions pass at 4 ranks. Renaming them to `test_*` would move
   the feature from *no MPI evidence* to among the best-covered in the release, and would put the one
   real bug in front of CI.
2. **The `mesh-adaptation` manifest entry is mis-scoped.** Its `validation.paths` name tests that
   exercise `mesh.remesh()` and hand-built multigrid hierarchies, not `adapt()`; one listed path,
   `tests/test_0760_mesh_ot_adapt.py`, no longer exists and is silently dropped. It has been passing
   for the wrong reason.
3. **Three Supported features rest on serial evidence alone:** `analytic-solutions`,
   `materials-system` and `stress-visualisation`. They passed at 4 ranks on 2026-09-24, but that was
   a one-off experiment, not something CI repeats. `analytic-solutions` is arguably exempt, since it
   is closed-form sympy with no distributed mesh and passing under MPI proves nothing. The other two
   are not.
